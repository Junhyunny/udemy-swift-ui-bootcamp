# "unable to type-check this expression in reasonable time" — 컴파일러가 타입 추론을 포기할 때

## 질문이 나온 코드

`chapter-156/chapter-156/ContentView.swift`

```swift
struct ReusableSegmentedControl<T: SegmentItem>: View
where T.RawValue == String {
    @Binding var selection: T
    private let items: [T] = T.allCases as! [T]
    @Namespace private var animation

    let colorProvider: (T) -> Color

    var body: some View {
        HStack(spacing: 0) {
            ForEach(items, id: \.self) { item in
                HStack(spacing: 8) {
                    Image(systemName: item.icon)
                    Text(item.rawValue)
                }
                .font(.headline)
                .padding(.vertical, 12)
                .frame(maxWidth: .infinity)
                .foregroundStyle(selection == item ? .primary : .secondary)
                // ...
            }
        }
    }
}
```

`item`의 타입이 제네릭으로 정리되기 전에는 이 오류가 났다.

```text
The compiler is unable to type-check this expression in reasonable time;
try breaking up the expression into distinct sub-expressions.
```

`SegmentItem` 프로토콜을 만들고 `AppTab`이 채택하게 한 뒤 `ReusableSegmentedControl<T: SegmentItem>`으로 묶으니 해결됐는데, **왜 그랬는지**가 질문이다.

> 참고: 고치기 전 코드는 커밋되지 않아 git에 남아 있지 않다. 아래는 이 오류가 생기는 **원리**와, 지금의 수정이 왜 효과가 있었는지를 설명한다.

## 공부할 내용

### 결론 먼저

이 오류는 **버그도, 코드가 틀렸다는 뜻도 아니다.** "타입을 알아내는 계산이 너무 오래 걸려서 중간에 포기했다"는 뜻이다. Swift 컴파일러 문서가 직접 말한다.

> Solving the constraint systems generated by the Swift language can, in the worst case, **require exponential time.** Even the classic Hindley-Milner type inference algorithm requires exponential time, and the Swift type system introduces additional complications, especially overload resolution.

핵심 단어는 **지수 시간(exponential time)**과 **오버로드 해석(overload resolution)**이다. 표현식에 타입이 확정되지 않은 조각이 하나 늘 때마다 컴파일러가 따져 봐야 할 경우의 수가 **곱셈으로 불어난다.**

수정이 통한 이유는 한 줄로 요약된다. **`item`의 타입을 컴파일러에게 확정해 줘서, 따져 볼 경우의 수를 곱셈에서 1로 만들었다.**

### Swift가 타입을 정하는 방식 — 제약 조건 풀기

Swift는 "왼쪽부터 순서대로 타입을 정한다"가 아니라 **표현식 전체를 하나의 연립방정식으로 세워 푼다.** 컴파일러 문서가 정리한 단계는 이렇다.

> **Constraint Generation:** Given an input expression and (possibly) additional contextual information, generate a set of type constraints that describes the relationships among the types of the various subexpressions.
>
> **Constraint Solving:** Solve the system of constraints by assigning concrete types to each of the type variables in the constraint system.

예를 들어 `Text(item.rawValue)`를 만나면 이런 식이다.

```text
T0 = item 의 타입
T1 = item.rawValue 의 타입
T2 = Text(...) 의 결과 타입

제약:
  T0 에 rawValue 라는 멤버가 있어야 한다     → T1 이 정해짐
  Text 의 어떤 이니셜라이저가 T1 을 받아야 한다
  T2 = Text
```

### 오버로드가 경우의 수를 곱한다

문제는 `Text(_:)` 같은 이름이 **하나가 아니라는 것**이다. 컴파일러 문서의 설명이다.

> Overloading in the type checker is modeled by introducing a fresh type variable (call it `T0`) for the type of the reference to an overloaded declaration. Then, a **disjunction constraint** is introduced, in which each term binds that type variable ... to the type produced by one of the overloads in the overload set.

`disjunction`은 "이것 아니면 저것"이다. 후보가 여러 개면 **하나씩 넣어 보고 전체가 풀리는지 확인**해야 한다.

```text
Text(_:) 의 후보가 5개
  ×
Image(systemName:) 의 후보가 3개
  ×
.foregroundStyle(_:) 의 후보가 여러 개
  ×
삼항 연산자 ? : 의 양쪽 타입 후보
  ×
.primary / .secondary 가 어느 타입의 멤버인지 후보
        ↓
  경우의 수가 곱셈으로 불어난다
```

`item`의 타입이 확정되어 있으면 첫 칸이 **1**로 고정되고, 그 뒤 곱셈이 전부 줄어든다. 반대로 `item`의 타입이 미정이면 **모든 칸이 동시에 미정**이 되어 폭발한다.

컴파일러 문서는 이 폭발을 해결책 점수로 가지치기한다고 설명한다.

> If the score of the current solution is ever greater than that of the best complete solution, it abandons the current solution and backtracks to continue its search.

가지치기를 해도 한계가 있다. 그래서 **시도 횟수가 일정 선을 넘으면 포기하고** 우리가 본 그 오류를 낸다. 컴파일러 소스의 진단 정의가 정확히 그 문장이다.

```text
ERROR(expression_too_complex,none,
      "the compiler is unable to type-check this expression in reasonable time; "
      "try breaking up the expression into distinct sub-expressions", ())
```

Swift 컴파일러 성능 문서도 이 지점을 알려진 약점으로 인정한다.

> Expression type inference solves constraints inefficiently, and can sometimes behave **super-linearly or even exponentially.**

### SwiftUI에서 유독 자주 터지는 이유

SwiftUI의 `body`는 **modifier 체인 전체가 하나의 거대한 표현식**이다.

```swift
HStack(spacing: 8) { Image(...); Text(...) }
    .font(.headline)
    .padding(.vertical, 12)
    .frame(maxWidth: .infinity)
    .foregroundStyle(selection == item ? .primary : .secondary)
    .background { ... }
    .contentShape(.rect)
    .onTapGesture { ... }
```

여기에 세 가지가 겹친다.

| 요인 | 효과 |
|---|---|
| modifier마다 반환 타입이 달라짐 (`ModifiedContent<...>`) | 중첩 제네릭이 깊어짐 |
| `.headline`, `.primary`, `.rect` 같은 **암시적 멤버 표기** | "어느 타입의 멤버인가"가 전부 미지수 |
| `@ViewBuilder` 클로저 | 클로저 내부까지 같은 방정식에 포함됨 |

특히 **`.primary` 같은 점 표기**가 위험하다. 앞에 타입 이름이 없으므로 컴파일러가 문맥에서 역추론해야 한다. `Color.primary`인지 `HierarchicalShapeStyle.primary`인지는 `foregroundStyle`의 어떤 오버로드가 골라지느냐에 달렸고, 그건 다시 앞의 뷰 타입에 달렸다. **꼬리를 무는 구조**다.

여기에 `item`의 타입까지 미지수면 방정식이 감당할 수 없어진다.

### 직접 재현해 보기

SwiftUI가 없어도 같은 오류를 만들 수 있다. `Int`와 `Double` 리터럴을 섞어 연산자를 길게 이으면 된다.

```swift
func f() -> Double {
    let a = 1
    let b = 2.0
    return [a, a, a].reduce(0, +) + b + Double(a) * 2 - 1 + 3 * 4.0 - 2 + 1.5 * 2 - 3 + 4 * 1.0
}
```

```text
error: the compiler is unable to type-check this expression in reasonable time;
       try breaking up the expression into distinct sub-expressions
warning: expression took 1730ms to type-check (limit: 1ms)
```

`+`와 `-`와 `*`는 각각 오버로드가 수십 개고, 숫자 리터럴은 `Int`도 `Double`도 될 수 있다. 연산자를 하나 늘릴 때마다 조합이 곱해진다. **뷰나 제네릭과 무관한, 순수한 타입 추론 폭발**이다.

같은 식을 중간 변수로 쪼개고 타입을 적어 주면 곧바로 통과한다.

```swift
func f() -> Double {
    let a = 1
    let b = 2.0
    let sum: Double = Double([a, a, a].reduce(0, +))
    let part1: Double = sum + b + Double(a) * 2 - 1
    let part2: Double = 3 * 4.0 - 2 + 1.5 * 2 - 3 + 4 * 1.0
    return part1 + part2
}
```

`-warn-long-expression-type-checking=100`으로 재봐도 경고가 하나도 뜨지 않는다. **1730ms → 100ms 미만**이다. 고친 것은 로직이 아니라 **컴파일러가 풀어야 할 방정식의 크기**뿐이다.

### 왜 이번 수정이 통했나

수정 전후에서 `item`에 대해 컴파일러가 아는 것이 이렇게 달라졌다.

```text
[수정 전]  item 의 타입이 미정 또는 제약이 약함
   item.icon      → "icon 이라는 멤버를 가진 타입이 무엇이든"  (후보 다수)
   item.rawValue  → "rawValue 를 가진 타입이 무엇이든"        (후보 다수)
   selection == item → == 오버로드 후보 다수
        ↓
   위 미지수들이 modifier 체인의 미지수와 전부 곱해짐 → 폭발

[수정 후]  item: T,  T: SegmentItem
   item.icon      → SegmentItem 이 var icon: String 을 요구 → String 확정
   item.rawValue  → where RawValue == String        → String 확정
   selection == item → SegmentItem: Hashable → == 하나로 확정
        ↓
   미지수가 사라져 modifier 체인만 남음 → 풀린다
```

프로토콜이 한 일은 **"이 타입에는 이런 멤버가 이런 타입으로 있다"를 컴파일러에게 미리 약속해 준 것**이다. 각 조각이 정확히 어떤 미지수를 없앴는지 보면 이렇다.

| 선언 | 없앤 미지수 |
|---|---|
| `var icon: String { get }` | `item.icon`의 타입 → `String` |
| `RawRepresentable` + `where RawValue == String` | `item.rawValue`의 타입 → `String` |
| `Hashable` | `selection == item`의 `==` 후보 → 1개 |
| `Hashable` | `ForEach(items, id: \.self)`의 `id` 타입 |
| `CaseIterable` | `T.allCases`의 존재와 타입 |
| `var color: Color { get }` | `item.color`의 타입 → `Color` |

**제네릭 + 프로토콜 제약은 추상화 도구이기도 하지만, 동시에 타입 추론의 탐색 공간을 잘라 내는 도구**이기도 하다. 이 경우가 후자의 효과를 본 사례다.

관련 개념은 [Swift 제네릭 문서](./swift-generics.md), [프로토콜 합성 문서](./protocol-composition-and-type-combining.md), [`where` 키워드 문서](./where-clause-usages.md)에 정리되어 있다.

### 진단 도구 — 어느 표현식이 느린지 찾기

오류가 난 줄이 **진짜 원인이 아닐 때가 많다.** 컴파일러는 표현식 전체를 하나로 보므로, 실제 범인은 같은 체인의 다른 줄일 수 있다. 시간을 재서 찾는다.

| 플래그 | 하는 일 |
|---|---|
| `-warn-long-expression-type-checking=<ms>` | 표현식 타입 검사가 n ms를 넘으면 경고 |
| `-warn-long-function-bodies=<ms>` | 함수 본문 타입 검사가 n ms를 넘으면 경고 |
| `-warn-long-expression-type-checking-scopes=<n>` | solver scope를 n개 넘게 쓰면 경고 |
| `-warn-long-expression-type-checking-trail=<n>` | solver trail step을 n개 넘게 쓰면 경고 |
| `-debug-time-expression-type-checking` | 모든 표현식의 소요 시간을 출력 |

명령줄에서는 이렇게 쓴다.

```bash
swiftc -typecheck -Xfrontend -warn-long-expression-type-checking=100 MyFile.swift
```

Xcode에서는 **Build Settings → Other Swift Flags**에 넣는다.

```text
-Xfrontend -warn-long-expression-type-checking=100
-Xfrontend -warn-long-function-bodies=100
```

빌드가 느릴 때 어느 뷰가 범인인지 찾는 데도 그대로 쓸 수 있다.

### 고치는 방법 — 효과가 큰 순서

**① 타입을 명시한다** (가장 효과적)

```swift
let color: Color = selection == item ? .primary : .secondary   // 타입을 적어 준다
```

미지수 하나를 통째로 지운다.

**② 제네릭 파라미터에 프로토콜 제약을 건다**

이번 수정이 이것이다. 멤버의 타입을 컴파일러에게 약속한다.

**③ 표현식을 쪼갠다**

오류 메시지가 직접 권하는 방법이다. 중간 변수로 나누면 방정식이 작은 것 여러 개로 갈라진다.

```swift
private func label(for item: T) -> some View {
    HStack(spacing: 8) {
        Image(systemName: item.icon)
        Text(item.rawValue)
    }
}
```

**④ 암시적 멤버 표기 앞에 타입 이름을 적는다**

```swift
.foregroundStyle(selection == item ? Color.primary : Color.secondary)
```

`.primary`가 어느 타입의 멤버인지 찾는 일이 사라진다.

**⑤ 뷰를 별도 `struct`나 `@ViewBuilder` 프로퍼티로 분리한다**

`body`가 커질수록 위험하다. 뷰를 나누면 각 `body`가 독립된 작은 방정식이 된다. [`@ViewBuilder` 함수 vs 별도 `View` 구조체 문서](./viewbuilder-vs-view-struct.md)와 이어진다.

**⑥ 숫자 리터럴 연산 체인을 줄인다**

`Int`/`Double` 혼용이 특히 비싸다. 명시적으로 `Double(...)`로 변환하고 중간 상수를 둔다.

### 헷갈리기 쉬운 것 — 이건 런타임 문제가 아니다

| | 타입 검사 시간 | 앱 실행 성능 |
|---|---|---|
| 언제 | **컴파일 중** | 실행 중 |
| 원인 | 제약 조건 조합 폭발 | 알고리즘·렌더링 |
| 고치면 | 빌드가 빨라짐 | 앱이 빨라짐 |

**표현식을 쪼개도 앱은 하나도 빨라지지 않는다.** 타입이 정해진 뒤의 코드는 완전히 동일하다. 순수하게 **컴파일 시간**만의 문제다.

## 체크리스트

- [ ] 오류 문구가 "코드가 틀렸다"가 아니라 "계산을 포기했다"는 뜻임을 설명한다.
- [ ] 제약 생성 → 제약 해결 두 단계를 각각 한 문장으로 요약한다.
- [ ] 오버로드가 disjunction 제약으로 모델링되어 경우의 수가 곱해지는 과정을 설명한다.
- [ ] 위의 `Int`/`Double` 혼용 예제로 오류를 직접 재현한다.
- [ ] 같은 식을 중간 변수로 쪼개고 오류가 사라지는 것을 확인한다.
- [ ] `-Xfrontend -warn-long-expression-type-checking=100`을 Xcode Other Swift Flags에 넣고 빌드해 본다.
- [ ] 이 프로젝트에서 가장 오래 걸리는 표현식을 찾아 본다.
- [ ] `SegmentItem`의 `icon` 요구사항을 지우고 오류가 어떻게 바뀌는지 관찰한다.
- [ ] `where RawValue == String`을 지우고 `Text(item.rawValue)`의 오류를 확인한다.
- [ ] `.primary`를 `Color.primary`로 바꿔 타입 검사 시간이 줄어드는지 측정한다.
- [ ] 타입 검사 시간과 앱 실행 성능이 별개임을 설명한다.
